# Browse projection cache implementation notes

The browse cache stores a bounded serialized SQLite base projection in the site Redis cache. Every request restores it into its own temporary SQLite file, then applies its page, sort, group, and export-facing projection work locally. Entries expire after 15 seconds and are bypassed above 4 MiB. Cache keys include site, account, canonical query and resolved date bounds, source generation, current permission signature, configuration signature, and implementation version. The key deliberately omits page, sort, and group selection so those views can reuse the same filtered source projection.

`before_request` starts a cacheable snapshot only for the named browse/report methods and only after confirming a clean transaction with no pending callbacks. It ends any earlier read-only repeatable-read snapshot after Frappe has initialized the request and session, captures the generation and calculation-start time, and leaves the request uncached if it cannot prove that boundary is safe. Cache-disabled, refresh, test, job, write, export, and active-repost contexts use a new calculation timestamp and do not restore or store shared projections. A stale request timestamp is never used when permission or generation context capture failed. If Redis becomes unavailable after a cache restore, the projection is discarded and the clean owned read snapshot is restarted before an uncached source rebuild; if pending writes or callbacks prevent a safe restart, the request gets a retry error rather than cached data.

Cache authorization is checked at request capture, before restoring an entry, and after building a projection. The fingerprint reads the current account's enabled/type/role-profile state, direct and profile roles, role definitions, applicable DocPerm and Custom DocPerm rows, User Permissions, and both direct and `everyone=1` DocShare grants. These reads use SQL-backed Frappe APIs instead of the current user's role memoization. The app gate separately reads the current enabled System User and System Manager grant directly from SQL, so a stale Frappe role list cannot keep the app open after System Manager is revoked. A cache-failure rebuild rechecks that gate after restarting its owned read snapshot. The source/configuration signature includes the current Temple Inventory company and singleton modified timestamp, the durable app-owned `ti_read_generation` value, and the latest Repost Item Valuation modification timestamp. If Redis is unavailable, cache reuse and storage fail open to an ordinary authorized calculation; authorization exceptions are not converted into cache misses.

A restored snapshot is checked against its calculation-start time again after local sort/group construction. If it crosses the 15-second age limit while the temporary projection is being prepared, the app discards it, restarts the clean owned read snapshot, rechecks app authorization, and builds from current ERPNext source data. A fresh uncached calculation may still return to its current caller when its own work exceeds the reuse limit; it is simply not stored for reuse.

## Invalidation audit

`hooks.py` registers the cache handler for document lifecycle events, but `read_cache.invalidate_after_commit` filters the wildcard to the source/auth/configuration doctypes in `READ_DOCTYPES`. This covers Item, Item Group, Warehouse, Batch, Company, Stock Entry and Stock Reconciliation, Inventory Activity and its Activity Type, source Purchase/Sales documents and bundles, File references, Temple Inventory Settings, and relevant role/permission documents. Repeated events within one transaction advance the durable revision once. Redis generation publication is queued after commit; rollback clears the scheduled state without publishing.

User saves advance the revision for inserts/deletes and changes to enabled state, user type, role profile, or the persisted role child list. Login-only last-active updates do not invalidate all inventory projections. Has Role, Role, Role Profile, DocPerm, Custom DocPerm, DocType, User Permission, and DocShare changes have source document hooks. `frappe.clear_cache()` has an app hook for global metadata/auth cache clears. User-only and doctype-only cache clears do not run Frappe's global `clear_cache` hooks, so relevant source document events and the fresh permission fingerprint remain the invalidation paths for those changes.

The app's `configuration.repair_pointer` uses `settings.db_set`, which bypasses ORM events. Frappe's `Database.set_value` documentation confirms that it does not invoke document events; the settings update advances its `modified` singleton value, which is included in `_configuration_signature`, and cache generation must still be invalidated when a source configuration write is performed through an eventful path. The separate durable read generation is changed only by the cache invalidation code; it does not repurpose the settings modification timestamp. `tabSingles` has only a nonunique `(doctype, field)` index, so a SQL upsert cannot increment this field safely. The app now uses a locking current-read and a transactional update, with a DocType-row-serialized initialization path when the singleton field does not exist.

ERPNext's stock repost path contains the direct-SQL exception: `stock_ledger.set_as_cancel` directly updates `tabStock Ledger Entry`, while Repost Item Valuation workers can rebuild stock ledgers and commit an `In Progress` state before finishing. Cacheable reads check for an active repost and bypass projections while one is running. Frappe's `after_job` hook receives the completed job method name; the app recognizes repost/stock-ledger worker names, commits a durable generation bump after the repost's direct writes, and then advances Redis generation. Other in-app stock/count writes use native Stock Entry or Stock Reconciliation document events. The audit did not identify another app-owned direct write to the queried source tables; external SQL scripts remain outside app hook coverage and must call the documented invalidation path after commit.

## Verification

The hardened native runner `temple_inventory.tests.test_native_inventory.run` sets `frappe.flags.in_test`, rejects inner commits, and rolls back in `finally`, because `bench execute` commits after a successful return. It now compares raw Temple Inventory Settings Singles and Warehouse/Item/Stock Entry counts after rollback and fails if any persisted data changed. The final frozen-source run passed 132/132 native scenarios in `/tmp/ti-standardization-review/C-native-final-verified.log`, including preference, schema, history, grouping, and cache tests. The before/after audit matched exactly: 29 Warehouses, 164 Items, 15 Stock Entries, and all Settings Singles unchanged. Focused history/auth/cache checks passed 7/7 in `/tmp/ti-standardization-review/C-focused-history-auth-retry.log`; focused timestamp-isolation cases passed 6/6 in `/tmp/ti-standardization-review/C-context-isolation.log`.

`tests/read_cache_benchmark.py` contains a read-only service benchmark plus two explicit live probes. The service benchmark reports source-builder call counts, response size, and elapsed time for stock, expiry, movement summary/records, loan items/records, report page/group paths, dashboard overlap, explicit refresh, and a new-generation miss. Run it only after a quiet site reset or other authorized live window:

```sh
bench --site development.localhost execute temple_inventory.tests.read_cache_benchmark.run
```

`run_concurrent_cold_miss` starts two synchronized equivalent reads on separate Frappe thread-local database connections and counts calls to the actual `stock_rows` source builder. With a 3-second bounded Redis lock wait, both requests returned the same snapshot and matched count 163 in 1.87s/1.96s, with one source build; see `/tmp/ti-standardization-review/C-concurrent-cold-miss-final.json`. The earlier 200ms wait produced two builds, so the bound was raised to three seconds based on this measured inventory build. After the change, the focused Redis base-projection/waiter regression passed 1/1 with a matching rollback audit in `/tmp/ti-standardization-review/C-focused-lock-wait-final.log`.

`run_invalidation_contract_probe` warms the same projection, saves a temporary Item description through normal document hooks, commits, then verifies a new source build. It restores the original description and preserves native stock, although Frappe updates that Item's `modified` timestamp as part of the normal save. It then creates a temporary app-enabled account, warms its report, revokes System Manager through a separate committed Frappe connection while retaining Stock User, and verifies the next read is denied. Cleanup removed the temporary account and restored the Item text. The probe output is `/tmp/ti-standardization-review/C-invalidation-contract-probe.json`; the cleanup check found no remaining artifacts, unchanged settings pointers, and row counts 29/164/15 in `/tmp/ti-standardization-review/C-probe-final-cleanup.json`. This exercises an Item metadata write rather than a stock-quantity write; the stock ledger was not changed.

For actual HTTP timing and serialized response sizes, `/tmp/ti-standardization-review/cache-http-perf.cjs` exercises the same endpoints through the authenticated API request lifecycle. It requires `TI_BENCH_PASSWORD` in the caller environment, uses the session CSRF token, and records refresh/first/repeat timings for stock, expiry, movement items/records, and loan items/records plus page/group/dashboard calls. It does not embed credentials. The direct service probe completed with one cold source build per view, no source calls for repeat/page/group/dashboard reuse, and fresh builds for explicit refresh and generation invalidation; see `/tmp/ti-standardization-review/C-cache-perf-bench.json`.
